# Crew Phase 4: Group Chats Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Group chats in Crew on top of Hermes's own rooms: a Groups sidebar section, New group, a group chat with @mention routing, topics, live "working" rows, approvals in groups, a group panel, and Delete — the same groups the official Webapp shows.

**Architecture:** The Crew server is the only thing that talks `groups.*` to Hermes. One `group-rpc` module pins `profile:"default"` and sends Hermes's exact params. A group watcher polls Hermes (5 s list, 2 s per active room), publishes `CrewState.groups`, bridges room approvals into the existing `PendingStore`, and marks members working. REST routes under `/crew/groups` do every mutation and serve the room log. The browser reduces log events into chat items and never sends `groups.*` frames (the `/api/ws` guard refuses them).

**Tech Stack:** Server: Node 24, Hono, Zod 4, Vitest, `ws`. Web: React 19, Vite 8, Tailwind v4, shadcn base-nova (Base UI), react-router-dom 7, Vitest + jsdom + Testing Library. e2e: Playwright in the VM.

**Spec:** `docs/superpowers/specs/2026-11-09-crew-phase4-group-chats-design.md` (§12 builder-check rulings override earlier text). Facts: `docs/phase4/hermes-facts.md` ("facts §n").

## Global Constraints

- Every `groups.*` call carries `profile: "default"` (`GROUP_OWNER_PROFILE`), and only the keys Hermes accepts for that method (facts §1.1, §1.3). `groups.context` always sends `purpose` and `notes`.
- Member rows: `{member_id: profile, profile, handle: profile === 'default' ? 'hermes' : profile, target: {kind:'local', profile}}` plus `display_name` only when the profile has a non-empty Hermes `display_name`. `room_id` = `crypto.randomUUID()`. Group name trimmed, 1–64 chars; default = picked bots' Crew titles joined with ", ".
- Hermes identifier rule for `thread_id`/`event_id` from the browser: `^[A-Za-z0-9][A-Za-z0-9._:-]*$`, ≤ 128 chars.
- Mention rule (port of Hermes, facts §3.2): `/@([A-Za-z0-9][A-Za-z0-9._:-]*)/g`, casefold match against member **handles** only; `@all`/`@everyone` = all; unknown ignored.
- Poll cadence: list every 5000 ms; active room state every 2000 ms; stalled after 120 000 ms without progress; history window 300 events; preview tail 20 events, preview text first line ≤ 80 chars.
- Model calls only on: send, Allow once, Keep going, Try again. No other code path may cause one. **Implementer subagents never run e2e specs tagged `@model`** (credit ≈ $0.34); only the controller runs them, once.
- No new npm dependency. CSP unchanged. No new ports. No writes to any Hermes config. Never touch the user's bots (default/"Hermes", reese, x) in tests.
- Project rules: Zod at server boundaries; files < 400 lines, functions < 50; theme tokens only (`web/test/app-states.test.tsx` "theme tokens only" scan must stay green); the dark-variant trap (an un-prefixed `bg-`/`border-` override on a shadcn variant that has `dark:` classes loses in dark mode — pick a variant without them or add `dark:` counterparts); status-neutral avatars (`{...bot, status:'idle'}`) while stale (Hermes not connected or Crew SSE down); no `console.log`; named exports except React components; commits are conventional, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Copy strings are fixed by the spec §2; use them verbatim.
- Test commands: server `cd app/server && npm test` (436 baseline), web `cd app/web && npm test` (535 baseline), types/build `npm run build` in each; `cd app/server && npm run vendor:check`.

## Review Focus

1. **Room owner drift:** any `groups.*` call without `profile:"default"` makes the room "vanish" (`permission_denied`). Every RPC test asserts the exact params object, including `profile`.
2. **Unaddressed follow-up cost:** a message with no mention in a continuing topic wakes every bot. The composer line must say "Everyone (n bots) will reply · @mention to ask one bot" before sending (Task 8 test `shows who will answer for a mention, two mentions, a trailing dot, a first message and a follow-up`).
3. **Approval duplicates:** a room approval might also reach the main watcher as an unanswerable `profile:'unknown'` entry; Needs you must show one card (Task 3 test `drops an unknown entry that duplicates a group approval`).
4. **Send retried after an uncertain failure** must reuse the same `eventId` and never show the message twice (Task 7 test `retries an unknown send once with the same eventId` and Task 5 reducer test `replaces the optimistic item when the log row arrives`).
5. **Group deleted elsewhere / Hermes restart** while the group is open: the view goes to the not-found pattern; an `epoch` change reloads history (Task 7 tests `goes to the not-found pattern when the group disappears`, `reloads when the epoch changes`).

  export interface GroupWatcher {
    state(): GroupsState
    /** Raw pending actions per room, for the pending bridge (T3). */
    pendingActions(): ReadonlyMap<string, readonly HermesPendingAction[]>
    seatable(): ReadonlySet<string>
    onChange(listener: () => void): () => void
    /** Poll one room (state + tail) now; resolves when done. Unknown room → refreshes the list. */
    refreshRoom(roomId: string): Promise<void>
    refreshList(): Promise<void>
    stop(): void
  }
  export interface GroupWatcherDeps { rpc: GroupRpc; connected: () => boolean; onConnectionChange: (l: (connected: boolean) => void) => () => void; now: () => number; setInterval?: typeof setInterval; clearInterval?: typeof clearInterval }

  Behaviour: on (re)connect → `capabilities()`; `available = driver === true`; `seatable = seatable_profiles` (published in `GroupsState.seatable`, sorted); then `refreshList()`. Every 2000 ms: `state()` for each active room (and the tail when `latest_seq` moved). Calls per room are serialized (a room never has two calls in flight). A failed call keeps the last view. `onChange` fires only when `state()` output changed (deep-compare the published JSON). Rooms sorted by `updatedAt` desc.
