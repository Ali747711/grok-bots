# Crew Phase 7: App Connectors (Composio) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The user connects apps once through Composio in Crew, then gives each bot an access level per app; write actions ask first, and the Composio key never leaves Crew.

**Architecture:**
- Crew keeps the key in a 0600 file and calls Composio REST v3.1 through one injectable `fetch` client. Each bot with apps gets one direct-tools-only Composio session and one Hermes MCP server `crew_apps` (`trust: untrusted`) pointing at Crew's loopback relay `POST /mcp/<bot>` with a per-bot bearer token; Crew stores only the token's SHA-256.
- The relay checks the token in constant time, filters `tools/list`, refuses a disallowed `tools/call` locally, and forwards the rest to the bot's session with the key header.
- A level change builds a new session, then reconnects the Hermes server in the background (recipe in `connectors/policy.ts`, fixed by the Task 7 live proof). App trust prompts become Crew approvals limited to Allow once / Deny.

**Tech Stack:** Server: Node 24, Hono, Zod 4, Vitest, `node:crypto`, global `fetch`. Web: React 19, Vite 8, Tailwind v4, shadcn base-nova (Base UI), lucide-react, sonner, Vitest + Testing Library. e2e: Playwright against the live Crew (127.0.0.1:7070) and Hermes (127.0.0.1:9120).

**Spec:** `docs/superpowers/specs/2026-11-10-crew-phase7-connectors-design.md` (§11 overrides earlier text). Facts: `docs/phase7/hermes-facts.md` ("H§n") and `docs/phase7/composio-facts.md` ("C§n"; §10 is live-checked). The spec's "plan task 1" is this plan's **Task 7**, because it needs Tasks 1–6 deployed. 5. **Bots deleted outside Crew** (`deleteTestBots`, the Hermes UI). Expected: the record and session go within a minute, while a bot missing from a single roster read keeps its apps. ## Plan rulings (gaps closed here)

- **R1. Unconnected apps keep their tools.** A session includes a toolkit's allowed tools with or without an active account; Composio answers such calls with its own error (Task 7 records it). §11.3's "without tools" is met in the UI: the app shows "Not connected", and only switch-off works. This also lets Task 7 prove the trust gate without a GitHub sign-in.
- **R2. Hints** come from REST `GET /tools`: `annotations.readOnlyHint`/`destructiveHint` when boolean, else membership in `tags`. A missing destructive hint on a non-read-only tool counts as destructive (the MCP default). Task 7 checks them against the session's MCP annotations.
- **R3. Relay messages.** One JSON object per body. The relay forwards `initialize`, `ping`, `notifications/*`, JSON-RPC responses (no `method`; an `id` and `result`/`error`), `tools/list` (filtered) and a `tools/call` whose `params.name` is allowed. Anything else gets a local JSON-RPC error.
- **R4. Relay errors after the token check** are HTTP 200 JSON-RPC errors (−32603, `RELAY_TEXT`), because a 401 makes Hermes say "run `hermes mcp login`" (H§8). A failed notification gets 202 with no body.
- **R5. URLs.** A session `mcp.url` must be `https:` on `backend.composio.dev`, and a sign-in `redirect_url` must be `https:` on `composio.dev` or a subdomain; anything else is `composio_unavailable`. Every Composio fetch uses `redirect: 'error'`.
- **R6. Reconnect** (`RECONNECT`), in the background, coalesced per bot, each toggle under `withBotLock`: disable → `reload.mcp {profile, confirm: true}` (if `nudge`) → wait `gapMs` → enable, only if the record and a key still exist → `reload.mcp` with the canonical chat (if `nudge`). It is scheduled only when the allowed set changed; a disabled server is simply enabled.
- **R7. Tokens** exist only in the `mcp.servers.add` call. A record whose server is gone gets a new token and hash. Apps `{}` removes the server, env var, session and record; without a key, the session stays at Composio.
- **R8. One removal path,** for turn-off and the create strip (§11.6): REST `DELETE /api/mcp/servers/crew_apps?profile=`, then `DELETE /api/env {key: 'MCP_CREW_APPS_API_KEY', profile}`, each ignoring 404. This writes the same config as `mcp.servers.remove`.
- **R9. Approvals off** means `approvals.mode` is YAML `false` or `'off'` in any case (Hermes `_normalize_approval_mode`). Only `read` is offered (a higher level gets 409 `level_unavailable`); a later switch to off is clamped to Read only within a minute, from the sandbox roster's config read; a chat's `/yolo` is not in config (a documented limitation).
- **R10. Orphan sweep:** a record is forgotten after its bot is missing from two roster syncs at least 30 s apart. An empty roster is ignored, and a bot that reappears resets.
- **R11. Sign-ins are stored,** so they survive restarts. After 10 minutes, the 60 s sweep or a poll deletes the account and the entry. A `failed` one is deleted at once.
- **R12. One account per app:** connect answers 409 `already_connected` when the toolkit has an `ACTIVE` account.
- **R13. A corrupt `connectors.json`** is moved aside like `triggers.json`, keeping a `userId` that still parses as a UUID.
- **R14. The key.** Saving checks it, saves it, then resumes in the background (rebuild each session, then enable its server). Removing awaits the per-bot disables (best-effort, logged), then deletes the file. `GET` answers `{configured}` only; "Key not accepted" shows after a refused save, or when an apps route answers `key_rejected`.
- **R15. Dialogs from the Profile panel** open through `window` `CustomEvent('crew:open-dialog', {detail: 'apps' | 'settings'})`, handled by `RosterFooter`.
- **R16. App prompt recognition** (Task 7's payload may replace it): `surface === 'mcp-trust/crew_apps'`, or `description` starting `Server 'crew_apps' is configured 'trust: untrusted'.`, or `command` matching `/^MCP tool '([^']+)' on UNTRUSTED server 'crew_apps' wants to run\./` (Hermes `mcp_tool_handlers.py`). Arguments were cut when `command` ends with `\n... [arguments truncated]`. Recognition only removes choices, and the store enforces it.
- **R17. Sign-in tab:** `window.open(url, '_blank', 'noopener,noreferrer')` right after the POST. The waiting state always shows the "Open the sign-in page" link (`target="_blank" rel="noopener noreferrer"`).
- **R18. One model turn at "Read and change"** (a read tool, then a write tool that is denied) covers both halves of acceptance 5 within §8's "one turn".

  export function filterToolsList(message: unknown, allowed: ReadonlySet<string>): unknown  // drops result.tools[] not allowed; nothing else changes
  export function rpcError(id: unknown, code: number, message: string): Record<string, unknown>
  // relay-routes.ts
  export interface RelayDeps { readonly store: Pick<ConnectorStore, 'record'>; readonly keys: Pick<KeyStore, 'get'>; readonly fetch: typeof fetch }
  export function relayRoutes(deps: RelayDeps | undefined): Hono<CrewEnv>   // undefined → 503 {error: 'apps_unavailable'}

  export const RELAY_PATHS = ['POST /mcp/*', 'GET /mcp/*', 'DELETE /mcp/*'] as const
  AppDeps.relay?: RelayDeps

- `routes.on(['POST', 'GET', 'DELETE'], '/mcp/:bot')` handles a request in this order (§11.8):
  1. Look up the record only when the name passes `PROFILE_NAME_RE`. If `!tokenMatches(record, parseBearer(authorization))`, answer 401 `{error: 'bad_token'}` without reading the body.
  2. `GET` → 405 with `Allow: POST, DELETE`; `DELETE` → 204.
  3. `readLimited(req, RELAY_MAX_BYTES)` null → 413 with `Connection: close`. Not JSON → 400 `rpcError(null, -32700, 'Parse error')`.
  4. A `judge` refusal → 200 `rpcError`. No key → 200 `rpcError(id, -32603, RELAY_TEXT.noKey)`; a notification gets 202.
  5. Call `fetch(record.mcpUrl, {method: 'POST', body, redirect: 'error', signal: AbortSignal.timeout(RELAY_TIMEOUT_MS)})`. It sends only `x-api-key`, `content-type: application/json`, `accept: application/json, text/event-stream`, and `mcp-protocol-version` when the client sent it.
  6. Upstream 401/403 → `rejected`. Another non-2xx or a throw → `unreachable`. 202 → 202 with no body.
  7. For `filter`: read at most 10 MiB and `parseUpstream` it. Answer `application/json` with `filterToolsList` of the message whose `id` matches; none, or unparseable → `unreachable`.
  8. Otherwise, stream the upstream body back with only its `content-type`.
- Logging: `log.info('mcp relay', {bot, method, tool?, outcome})` for each `tools/call`, refusal and failure. Never the body, the token or the key.
- `app.ts`: `PUBLIC_PATHS` gains `...RELAY_PATHS`; `originGuard(…, [...HOOK_PATHS, ...RELAY_PATHS])`; mount `relayRoutes(deps.relay)` beside `hookRoutes`, before the SPA.
