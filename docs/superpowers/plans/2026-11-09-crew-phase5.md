# Crew Phase 5: Event Triggers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Secret, HMAC-signed trigger URLs on a bot's routines. A GitHub or Generic event posted to `POST /hooks/<id>` runs the routine once, with the event as fenced outside data. Every event gets a logged outcome. Routines can also be "Only when triggered".

**Architecture:**
- Crew owns the receiver. `POST /hooks/:id` sits on Crew's server, exempt from the session and origin/CSRF guards; the host guard stays. It checks size → known → enabled → HMAC → dedupe → filter → limits.
- The runner reads the routine and creates a one-shot Hermes job (`[trigger:<id>] …`, schedule = ISO now, the routine's job-shaping fields copied). It fires `/trigger` without waiting, polls the job every 5 s, records the outcome and the run's session id, then deletes the one-shot.
- Trigger definitions, secrets, bounded event logs and dedupe ids live in `stateDir/triggers.json` (0600, atomic writes).
- The web adds a Triggers disclosure on each routine row, Add trigger / secret / events dialogs, and a "Runs" choice in the routine form.

**Tech Stack:** Server: Node 24, Hono, Zod 4, Vitest, `node:crypto` (HMAC, `timingSafeEqual`, `randomBytes`). Web: React 19, Vite 8, Tailwind v4, shadcn base-nova (Base UI), lucide-react, sonner, Vitest + jsdom + Testing Library. e2e: Playwright in the VM.

**Spec:** `docs/superpowers/specs/2026-11-09-crew-phase5-event-triggers-design.md` (§11 builder-check rulings override earlier text). Facts: `docs/phase5/hermes-facts.md` ("facts §n"). The "Plan rulings" below bind like the spec.

## Global Constraints

- **Credit:**
  - Model calls happen only on an accepted event (a hook request that passes every check), on **Send test event**, and on **Run now**. No other code path may cause one.
  - **Implementer subagents never run e2e specs tagged `@model` (`triggers-model.spec.ts`).** Only the controller runs it, once.
- **Hermes and the user's bots:**
  - No restarts of `hermes-gateway` or `hermes-dashboard`. Crew restarts (`systemctl --user restart crew`) are allowed for deploy checks.
  - No edits under `~/.hermes`. The source at `~/.hermes/hermes-agent` is read-only reference.
  - Hermes's webhook platform is neither used nor touched.
  - Never touch `default`, `reese`, `x` or `telegram`. Tests use only `crew-test` (title "Fixture") and `e2e<digits>`.
- **Dependencies and security headers:** no new npm dependency (`node:crypto` and the installed lucide-react cover it). CSP unchanged (`SPA_CSP` in `http/spa.ts`). No new ports.
- **Values:**
  - Limits per trigger: 10 runs per sliding hour (3600 s), 2 in flight.
  - Hook body ≤ 1 MiB (`1_048_576` bytes), read raw before parsing.
  - Payload ≤ 6000 chars; GitHub body ≤ 2000 chars; Generic timestamp within ±300 s.
  - Per trigger: the event log keeps the last 50 events and dedupe keeps the last 500 delivery ids. An event `detail` is ≤ 200 chars.
  - Poll every 5000 ms, for up to 30 min.
  - Trigger id = `randomBytes(16)` hex; secret = `randomBytes(32)` hex.
  - URL `http://127.0.0.1:7070/hooks/<id>`, built from `config.host` and `config.port`.
- **Hermes shapes (facts §8.3, §2b, spec §5, §11):**
  - One-shot: `POST /api/cron/jobs?profile=<bot>` with:
    - `name: "[trigger:<triggerId>] <routine title> · <event type>"`, `prompt`, and `schedule` as `YYYY-MM-DDTHH:MM:SS+00:00` (now);
    - each of `deliver, model, provider, base_url, skills, enabled_toolsets, workdir, script, context_from, timezone` that the routine has non-null (`deliver` defaults to `'local'`).
  - Fire: `POST …/<id>/trigger?profile=<bot>` with `timeoutMs: 0`, without waiting; a 409 is fine.
  - Read: `GET …/<id>?profile=`. Runs: `GET …/<id>/runs?profile=&limit=5`. Delete: `DELETE …/<id>?profile=`.
  - Recovery: `GET /api/sessions?source=cron&profile=<bot>&limit=50` → `{sessions: [{id, title, started_at}]}`.
- **Trigger-only routines:**
  - Created with schedule `0 3 1 1 *`, `paused: true`, `paused_reason: "crew:trigger-only"`.
  - The marker is restored with `POST …/pause` then `PUT …/<id>?profile=` `{updates:{paused_reason:"crew:trigger-only"}}`. Hermes clears the marker whenever it force-runs a paused job (`cron/jobs.py:1655, 2776`). The restore is UNVERIFIED live; Task 10 proves it.
- **Secrets:**
  - Compared with `timingSafeEqual`.
  - Never log headers, bodies, secrets or full trigger ids; log only the first 8 chars of an id.
  - A secret is sent only in the 201 create reply and in `POST …/secret`.
- **Project rules:**
  - Zod at server boundaries; files < 400 lines; functions < 50; no `console.log`; named exports except React components.
  - Theme tokens only: the "theme tokens only" scan in `web/test/app-states.test.tsx` stays green.
  - The dark-variant trap: an un-prefixed `bg-`/`border-` override on a shadcn variant that has `dark:` classes loses in dark mode. Pick another variant or add `dark:` counterparts. Reuse `RoutineRow`'s `GHOST` and switch classes.

- **Copy (verbatim):**

  - Routine row: "Only when triggered".

  - Trigger list: "Triggers (<n>)", "Add trigger", "No triggers yet."; source badges "GitHub" / "Generic".
  - Add trigger warning (§11.5): "Runs started by events use this routine's tools. Outside text could try to steer the bot; it is marked as data, and risky actions are refused because nobody is there to approve them."
  - Created dialog: "The secret is shown once." and "Reachable from this computer and your Mac tunnel; public access comes later."

## Review Focus

1. **Duplicate in flight:** GitHub retries a delivery while the first copy is still being accepted. Expected: exactly one run, and the retry gets `200 duplicate` (Task 5 test `runs once for two concurrent requests with the same delivery id`).
2. **Run now on an "Only when triggered" routine:** Hermes force-activates the job and clears `paused_reason`. Without the restore, every later event would get `409 routine paused` (Task 3 test `re-pauses a trigger-only routine with its marker after Run now`).
3. **Crew restarts with runs in flight:** started events are polled again and still count, so a restart neither loses results nor lifts the 2-at-once / 10-per-hour limits (Task 4 test `resumes started events after a restart and counts them against the limits`).
4. **Event text with backtick fences or `## ` lines:** it stays inside the data fence. Crew's own wrapper text never trips Hermes's fire-time scan, which would block every event (Task 4 tests `keeps a payload with backtick fences inside a longer fence` and `the fixed wrapper text trips none of Hermes's cron threat patterns`).
5. **A noisy sender floods the log while a run is in flight:** the run's outcome is still recorded (Task 1 test `never trims a started event out of the log`).

## Plan rulings (design gaps closed here)

- **R1. Credit-safe e2e (§11.8): a blocked routine, no `CREW_TRIGGER_LIMITS`.**
  - The no-model spec uses a trigger-only crew-test routine whose instruction contains "ignore all previous instructions". Hermes marks every one-shot of it BLOCKED before it builds the agent (`cron/scheduler.py:2292-2314`, "the agent was NOT run").
  - Why:
    - no service env change and no crew restart mid-suite;
    - the shipped 10/2 limits are the ones proven;
    - it also proves the "blocked" outcome end to end;
    - a guard stops the suite if the first accepted event is not `blocked`, so the worst case is one Haiku call.
- **R2. Run now on a trigger-only routine** re-pauses it and restores the marker (pause, then `PUT {updates:{paused_reason}}`). A user's pause, resume or delete during the run cancels the restore, just as it cancels the re-pause today.
- **R3. HTTP answers:**
  - routine deleted → `410 routine_deleted`;
  - routine normally paused → `409 routine_paused`;
  - Hermes refused the create → `502 hermes_refused`;
  - Hermes offline → `503 hermes_offline`.
  - Every error body is `{error:'<code>'}`.
- **R4. Outcomes for requests the spec left open:**
  - 413 on a known trigger → outcome `too_large`.
  - Unknown id (404) → one journal line without the id.
  - GitHub `ping` → `ignored` with detail "GitHub ping".
- **R5. Filters:**
  - The event filter matches exactly; an empty filter accepts all events.
  - The action filter is GitHub-only and applies only to events that carry an `action`, so `push` passes it.
- **R6. Names:**
  - A missing event type is `unknown` (GitHub) or `event` (Generic).
  - Header names are trimmed and cut to 64 chars; any character outside `[A-Za-z0-9._:/-]` becomes `_`.
  - A delivery id over 200 chars is replaced by its sha256 hex.
- **R7. Store:**
  - `started` events are never trimmed out.
  - `TriggerEvent` gains `endedAt`, used for history durations.
  - A corrupt `triggers.json` is moved to `triggers.json.corrupt-<ms>`, and Crew starts empty with one error line.
- **R8. One-shot gone on restart (§11.1):** look for cron sessions whose title starts with `[trigger:<id>]`, whose `started_at` is in `[event.at − 5 s, event.at + 30 min]`, and whose id no other event uses. Exactly one match → `finished` with that run. Otherwise → `failed` "lost on restart".
- **R9. Poll limit:** after 30 min the event becomes `failed` "no result after 30 minutes". The job is not deleted.
- **R10. Display:**
  - The routine-delete warning counts the web's trigger list; no server change.
  - The dialog shows one warning (the §11.5 text, which already covers approvals).
  - "⚡" is the lucide `Zap` icon.
  - The transcript shows "Instruction: …" plus "Event: <summary values joined by ' · '>". The raw fenced prompt is checked in the `@model` spec.
- **R11. Other choices:**
  - A finished one-time routine still fires its triggers.
  - Send test event uses the trigger's first filtered event type and action.
  - Deleting a bot leaves its triggers (they answer 410); cleanup is out of scope.

  ```ts
  export class TriggerStore {
    static load(file: string): Promise<TriggerStore>
    all(): readonly Trigger[]; forBot(bot: string): readonly Trigger[]; get(id: string): Trigger | undefined
    add(trigger: Trigger): Promise<void>
    update(id: string, patch: TriggerPatch): Promise<Trigger | undefined>
    remove(id: string): Promise<boolean>                       // drops its events and delivery ids too
    events(id: string): readonly TriggerEvent[]                // newest first
    lastEvent(id: string): TriggerEvent | null
    logEvent(id: string, event: TriggerEvent, deliveryId?: string | null): Promise<void>
    patchEvent(id: string, eventId: string, patch: EventPatch): Promise<TriggerEvent | undefined>
    seenDelivery(id: string, deliveryId: string): boolean
    recordDelivery(id: string, deliveryId: string): Promise<void>
    runsFor(bot: string, routineId: string): readonly TriggerRun[]       // events with a runId

  }
  ```

  - File shape (Zod-checked on load): `{version: 1, triggers, events: Record<id, TriggerEvent[]>, deliveries: Record<id, string[]>}`.
  - Every mutation replaces state in memory **synchronously** (new objects only), then queues a write of the latest snapshot.
    - Writes go through one serial promise chain.
    - A mutation's promise resolves once a write that contains it has finished. It rejects if that write fails; memory keeps the change, and the next write retries.
  - Write procedure (as `SettingsStore`): dir `0o700`; write `<file>.tmp` with `0o600` and `chmod`; then `rename`.
  - `logEvent` prepends the event. It trims to the 50 newest but never drops a `started` event (R7). In the same write it records `deliveryId` (last 500 kept).
  - `load` cases:
    - missing file → empty store;
    - invalid JSON or schema → rename to `<file>.corrupt-<Date.now()>`, `log.error('triggers file invalid, moved aside', {file})`, start empty;
    - any other error → throw.

### Task 2: Signature checks, payload parsing, limits

**Files:**
- Create: `app/server/src/triggers/verify.ts`, `app/server/src/triggers/payload.ts`, `app/server/src/triggers/limits.ts`
- Test: `app/server/test/trigger-verify.test.ts`, `app/server/test/trigger-payload.test.ts`, `app/server/test/trigger-limits.test.ts`

**Interfaces:**
- Produces (`verify.ts`):
  - `HeaderGetter {get(name: string): string | null}` (`Headers` fits).
  - `VerifyResult = {ok: true; eventType: string; deliveryId: string|null} | {ok: false; reason: string}`; `MAX_SKEW_S = 300`.
  - `verifyGithub(raw: Buffer, headers, secret): VerifyResult`:
    - checks `x-hub-signature-256: sha256=<64 hex, any case>` against HMAC-SHA256(secret, raw);
    - event type = `eventNameOf(x-github-event) ?? 'unknown'`; delivery = `deliveryIdOf(x-github-delivery)`.
  - `verifyGeneric(raw, headers, secret, nowMs): VerifyResult`:
    - `x-crew-timestamp` must match `/^\d{1,11}$/` and be within ±300 s of now;
    - `x-crew-signature: sha256=<hex>` is the HMAC over `` `${ts}.` `` + raw (§11.3);
    - event type = `eventNameOf(x-crew-event) ?? 'event'`; delivery = `deliveryIdOf(x-crew-delivery)`.
  - Reasons (exact): `'missing signature'`, `'signature does not match'`, `'missing or malformed timestamp'`, `'timestamp too old or too new'`.
  - Malformed hex never throws. Comparison is `timingSafeEqual` on equal-length buffers.
  - `signGithub(raw, secret): string` and `signGeneric(raw, secret, timestamp: string): string` both return `'sha256=<hex>'`.
  - `eventNameOf(v: string|null|undefined): string|null` (R6). `deliveryIdOf(v): string|null`: trimmed; empty → null; > 200 chars → sha256 hex.
- Produces (`payload.ts`):
  - `ParsedPayload = {kind:'json'; value: unknown} | {kind:'text'; text: string}`.
  - `parsePayload(raw, contentType: string|null): ParsedPayload` (§7):
    1. `application/x-www-form-urlencoded` with a `payload` param → JSON-parse the param; if that fails, the param is text.
    2. Otherwise JSON-parse the UTF-8 body, whatever the content type.
    3. Else text. An empty body is `{kind:'text', text:''}`.
  - `payloadAction(p): string|null` → `eventNameOf(value.action)` when the value is an object with a string `action`.
- Produces (`limits.ts`):
  - `TriggerLimits {perHour; concurrent}`; `DEFAULT_LIMITS = {perHour: 10, concurrent: 2}`.
  - `Acquire = {ok: true} | {ok: false; reason: 'hourly'|'concurrent'; detail: string}`. Detail: `` `${perHour} runs in the last hour` `` or `` `${concurrent} runs already running` ``.
  - `Limiter {tryAcquire(triggerId): Acquire; release(triggerId, ran: boolean): void; seed(triggerId, startedAt: readonly number[], inFlight: number): void}`.
  - `createLimiter(limits, now): Limiter` keeps state in memory, per trigger.
    - The hourly check runs first.
    - `tryAcquire` stamps the hour and takes an in-flight slot.
    - `release(…, false)` also removes the stamp.

    If the trigger was deleted meanwhile, still release the slot and delete the job.
  - `resume()` seeds the limiter from the log, then polls every `store.inFlight()` event. Hourly stamps come from events that have a `jobId` and `at ≥ now − 3600 s`. In-flight slots come from the `started` events.

    8. Filter miss → `ignored` with its detail, record the delivery → 200.
    9. `runner.start` → 202 `{status:'accepted', event: eventType, eventId}`, or the runner's status with `{error}`.
