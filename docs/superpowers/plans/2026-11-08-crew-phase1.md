# Crew Phase 1 Implementation Plan — work with existing bots

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Grok-Bot-style web app at http://127.0.0.1:7070 where the user sees their bots with live status, chats with each bot (streamed replies, collapsed work blocks, Stop), answers approval / question / secret cards in the chat or in a Needs-you inbox, and sees credit left.

**Architecture:** The Crew server (Phase 0) gains three things: it serves the built React app, its watcher becomes the single source of bot status + pending requests (pushed to browsers over SSE) and the single answer path for every request, and a usage endpoint. The browser keeps its own Hermes connection (through the Phase 0 WebSocket proxy) only for the open chat: loading history (REST), streaming events, sending and stopping.

**Tech Stack:** Node 24, TypeScript (strict, ESM), npm workspaces; server: Hono, ws, Zod, Vitest; web: Vite, React 19, Tailwind CSS v4, shadcn/ui (lucide icons), TanStack Query, react-markdown, Vitest + Testing Library (jsdom); e2e: @playwright/test (run on the Mac through the tunnel). Hermes v0.23.0 @ `2bd378ed1b8d6bf2192cb26e0a55ff3091e6bd19`.

**Spec:** `docs/superpowers/specs/2026-11-08-crew-app-design.md` (§2 goals 1–4, 9; §4 anti-goals; §6.4 approvals; §6.6 budget; §7 UI; §9 Phase 1 acceptance; "Phase 0 results"). Protocol facts: `docs/phase0/protocol.md`, `docs/phase0/approval-experiment.md`. UI reference: `docs/superpowers/specs/crew-mockup.html`.

## Global Constraints

- Everything from the Phase 0 plan's Global Constraints still holds (repo/branch workflow, loopback-only, Host/Origin/CSRF/cookie rules, token never reaches the browser or logs, no `console.log`, Zod at boundaries, files < 400 lines, functions < 50 lines, conventional commits). Branch: **`crew-phase1`** (from `crew-phase0`).
- Hermes protocol is **canonical session authority**. Use only the canonical shapes in this plan; key every session by the **`session_id` Hermes returns** (it can differ from the id sent); events carry no profile, so Crew keeps its own `session_id → bot` map.
- Bot chat = the hidden session titled exactly **`Bot Chat`**. Open: roster row has `canonical_session` → `session.resume {profile, session_id: canonical_session.resolved_id ?? canonical_session.id, omit_messages: true}`; no `canonical_session` → `session.create {profile, title: "Bot Chat", hidden: true, follow_profile_config: true}` (server-side find-or-create under a lock). Never create on a failed lookup.
- A connection must be **subscribed** (resumed) to a session before `prompt.submit` / `approval.respond` / `clarify.respond`; after every reconnect, re-resume before allowing send.
- Prompts arrive as events: `approval.request {prompt_id, execution_generation, command, description, choices, timeout_s?}`, `clarify.request {prompt_id, execution_generation, question, choices, multi_select}`, `*.settled {prompt_id}`. Answers: `approval.respond {session_id, execution_generation, prompt_id, choice}` → `{status: "resolved" | "already_resolved"}`; `clarify.respond {session_id, execution_generation, prompt_id, answer}` (`""` = skip; multi-select = JSON array string). `secret` / `sudo` arrive as server→client requests (`srq-…`), answered with `{value}`; **never answer any `srq-` with an error** (an error settles it as skipped).
- **All answers go through the Crew server watcher** (`POST /crew/requests/:id/answer`); the browser never calls `*.respond` itself. Render **only `choices` Hermes sent**. Expiry / resolution shown is what Hermes reports (`*.settled`, `request.cancel`) — no client timers.
- Send: `prompt.submit {session_id, text, submission_id: crypto.randomUUID(), surface: "hud"}`, RPC timeout **1 800 000 ms**; result `AdmissionStatus.status` `queued | started | terminal | unknown`. Stop: `session.interrupt {session_id, execution_generation}` using the highest generation seen for that session (snapshot, top-level `params.execution_generation` stamps, `session.info`, `approval.request`).
- Events: read `execution_generation` / `seq` at the **top level of the event params**, not in `payload`; `message.delta {text: null}` is a segment boundary; de-dupe text by `(turn_id, segment, offset)`; ignore `agent.step`; treat every `session.info` as a partial patch (`running` only when it is a boolean).
- Approvals expire after **1800 s** (`approvals.timeout`, set 2026-11-08). Secrets/sudo expire after 120 s (Hermes fixed).
- Rendering: markdown via `react-markdown` with **no raw HTML**; links only `http:`, `https:`, `mailto:`; approval cards always show the real `command` / `description`; no raw JSON elsewhere. Look: calm, minimal, one accent, light + dark (follow `crew-mockup.html`).
- Budget (§6.6): at most **2 bots working at once** (composer disabled with an explanation when 2 are working); credit pill cached **60 s**, states `ok | stale | unavailable`; per-bot spend labelled "estimate".
- SPA served by Crew with `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'` and `X-Content-Type-Options: nosniff`.

## Review Focus

1. **Connection drops mid-turn** (Hermes or Wi-Fi blip while a reply streams) → no duplicated or lost text, the chat re-subscribes before Send is enabled again. Tests: Task 6 `replayed frames do not duplicate text`, Task 7 `resubscribes open chat after reconnect and blocks send until done`.
2. **Two tabs open** → answering in one updates the other within a second; the second answer gets "already answered", not an error. Tests: Task 3 `broadcasts state to every SSE client`, Task 4 `second answer reports already_resolved`.
3. **Bot output with HTML / script / `javascript:` links** → shown inert. Test: Task 8 `markdown renders html as text and drops javascript links`.
4. **Hermes offline or signed out while the app is open** → a visible "Hermes is offline" / "signed out" banner, composer disabled, no blank screen. Tests: Task 3 `state reports hermes connection status`, Task 5 `shows hermes offline banner`.
5. **Huge tool output or very long reply** → UI stays usable: work-block details truncated to 4 000 chars with "Show more". Test: Task 8 `work block truncates long output`.
